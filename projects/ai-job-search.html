01 / THE PROBLEM

Job boards bury relevant roles under noisy algorithms and fragmented data.

Searching for software engineering positions across generalist job boards means sifting through hundreds of irrelevant postings, inaccurate location tags, and buried requirements.

General-purpose search algorithms on large job aggregators frequently return senior managerial roles, sales positions, or unrelated technical stacks when searching for entry-level or specialized developer roles. Furthermore, external job APIs return unpredictable payload structures: some omit salary fields, others nest location data three levels deep, and most bury remote/hybrid policies inside large blocks of unstructured text.

Without a disciplined collection and normalization pipeline, developers either miss opportunities due to minor title differences (e.g., "Python Developer" vs. "Backend Engineer") or waste hours manually parsing listings that don't match their work arrangement preferences.

AI Job Search solves this by establishing a deterministic four-stage data pipeline: querying external job boards via REST endpoints, mapping raw payloads to standardized Job dataclass models, expanding roles with semantic aliases, and filtering opportunities purely on clean, validated properties.

03 / ARCHITECTURE

Modular four-stage pipeline with strict separation of concerns.

The application follows a linear, decoupled architecture where each stage has a single, well-defined responsibility. Network communication is isolated at the edge, data is normalized into structured domain models, and filtering operates purely on clean domain instances.

04 / KEY DECISIONS

Design choices that keep the pipeline clean and extensible.

V1 was architected with clean separation of concerns, ensuring that modifying data sources, expanding filter rules, or altering output formats does not require rewrites across the application.

01

Decoupled Normalization Layer

Raw API payloads are never passed directly to filter functions. A dedicated normalizer transforms vendor-specific keys into a standardized Job dataclass. This guarantees that adding future job boards (such as Greenhouse, Lever, or LinkedIn) only requires a new normalizer function rather than alterations to downstream filtering logic.

02

Role Alias Expansion Engine

Job titles vary widely across companies. The role_aliases.py module maps broad target titles (e.g., "software engineer") to ten related industry titles, including "backend engineer", "full stack engineer", "python developer", and "site reliability engineer", significantly improving recall without requiring multiple manual queries.

03

Regex Work-Arrangement Extraction

Because job boards rarely enforce structured remote/hybrid tags, extract_work_arrangement evaluates description text using targeted regular expressions (such as hybrid|remote \d+ days (per|a) week) to reliably categorize listings as remote, hybrid, or onsite.

04

Defensive Dataclass Modeling

Domain models are declared using Python's @dataclass with explicit type hints and defensive field factories (e.g., employment_types: list[str] = field(default_factory=list)). This ensures strict schema validation and eliminates runtime AttributeError or mutable default bugs.

What V1 does not represent

No LLM integration: Despite the project name, V1 does not use an LLM (such as OpenAI, Gemini, or Claude). There is currently no automated résumé parsing, semantic embedding generation, or AI job scoring.

Commute time calculation: While max_commute_minutes is declared on the UserPreferences dataclass as a future schema placeholder, actual transit or distance calculation is not implemented in V1 filtering logic (which requires an external geolocation API).

CLI execution only: V1 is an independent Python command-line pipeline executed locally, not a deployed SaaS web dashboard, multi-tenant platform, or automated application bot.

Separate from real-world workflow: This standalone software project is completely separate from my personal real-world job-search workflows using LLM assistants.

07 / TAKEAWAY

What building a production-style data pipeline taught me.

Reliable software begins with disciplined data modeling and clean separation of concerns before adding complex features.

The most important design decision in AI Job Search was isolating external API payloads behind dedicated normalizer functions. By transforming messy, vendor-specific JSON dictionaries into immutable, strongly-typed Job dataclasses immediately upon ingestion, the filtering logic remained pure, testable, and completely independent of Adzuna's specific API schema.

Equally valuable was the discipline of incremental scoping: rather than attempting to build an all-in-one AI auto-apply tool, V1 focused strictly on building a reliable, fault-tolerant collection and filtering engine with 100% automated test coverage. This created a solid foundation that makes future integrations—like LLM scoring or database persistence—straightforward and clean.
